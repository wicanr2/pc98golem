# Spec 006：音訊——軟體音源 BIOS、驅動執行與 YM2203 合成

狀態：READY。

## 為什麼是這個形狀

PC-98 版《Pool of Radiance》的 `MSCDRV.EXE` **自己不排音序**：它把曲子的
壓縮串流展開成 NEC 音源 BIOS 的演奏資料區塊，交給 BIOS 播（spec 005）。
所以「把曲子變成音訊」有兩種做法：

| 做法 | 代價 |
|---|---|
| 靜態解析曲子資料，自己重寫展開器 | 快，但展開器是**重寫的**——寫錯會安靜地錯 |
| **跑原版驅動自己的碼**，攔它交給 BIOS 的東西 | 需要一顆 CPU 與一層軟體音源 BIOS |

pc98golem 有 CPU，所以走第二種。價值不在「也能出音訊」，在於**它是另一個
獨立來源**：靜態解析與實際執行兩邊的演奏資料必須逐位元組相同，
不同就是有一邊錯了。

## 1. 軟體音源 BIOS（`internal/soundbios`）

真的音源 BIOS 在 PC-9801-26K 音源板的 ROM 裡，我們沒有那顆 ROM，
**也不需要**——驅動只用五個命令，而且音高與時值都在曲子資料裡。

`INT D2h` 的實作範圍：

| AH | 命令 | 本層做什麼 |
|---:|---|---|
| `00` | INITIALIZE | 記下 `ES`（工作區段）|
| `01` | PLAY | 記下 `ES:BX`（演奏資料結構），標記開始播 |
| `02` | CLEAR | 記下 |
| `19` | ALLSTOP | 標記停止 |
| `1A` | CONTPLAY | 標記續播 |
| `16` | SETPARABLOCK | 音色參數塊：`internal/soundbios` 解版面並換算成晶片值 |
| 其他 | — | **記下並回報**，不靜靜當成 nop |

驅動用 `CEE0:0004 == $00D2` 認出音源板，再讀 `CEE0:0006` 當進入點。
本層在那個位址擺一份介面表讓偵測過關；`INT D2h` 由 `IntHook` 接管，
所以那個進入點永遠不會真的被執行。

**`INT 21h AH=31h`（TSR）也要接**：驅動安裝完就 TSR，沒有它機器會跑飛。

## 2. 跑驅動（`internal/mscdrv`）

一個位址都不寫死。流程完全照原版的安裝與呼叫路徑：

1. 把 `MSCDRV.EXE` 當一般 EXE 載入，從它自己的進入點跑到 TSR。
   跑完之後 `IVT[7Eh]` 就是驅動裝好的處理常式——**位址是它自己填的**。
2. 用 `INT 7Eh`／`AH=0`／`AL=曲號` 叫它播。驅動會建好工作區、
   呼叫 `INT D2h AH=01h PLAY`，被本層攔下來。
3. 之後**由本層當 BIOS 去抽資料**：每個聲道的工作區裡有一個 far 指標
   （BIOS 缺資料時要回呼的位置），照那個指標 far call 回驅動，
   一次拿一個演奏資料區塊，直到那個聲道的串流指標歸零。

第 3 步就是原版 BIOS 在做的事。差別只在時機：真機是缺資料才回呼，
這裡是一口氣抽完。**對曲子內容沒有影響**，因為抽取只看串流，不看時間。

### 收尾條件要說出來

會循環的曲子抽不完。抽取有上限，**碰到上限一定要標成截斷**——
不標的話「曲子就這麼長」與「我抽到一半就停了」長得一模一樣。

## 3. 音色參數塊

`DL=1` 是 BYTE 格式：與 WORD 格式（100 位元組）同一組欄位，一格一個位元組，
但 **LFO 速度仍是 WORD**，所以它之後的欄位整體位移一格，尾端補一格，
合計 52 位元組。版面表在 `internal/soundbios/patch.go`。

版面的三條不變量在原版音色上全部成立：運算元遮罩只用低四位元、
KS 四格落在 0..3、三個保留欄位（+41、+46、+51）恆為 0。

**欄位值不能直接寫進晶片。** NEC 的速率與準位是反向刻度：

```
KS/AR  = KS << 6 | (31 − AR 參數)      DR = 31 − DR 參數
SR     = 31 − SR 參數                  SL/RR = (15 − SL) << 4 | (15 − RR)
TL     = 127 − OUTPUT_LEVEL            DT/MUL = DETUNE << 4 | MUL（不截三位元）
```

照抄的症狀不是報錯，是**幾首曲子幾乎沒有聲音**。key-on 也不是永遠 `$F0`：
發聲的運算元由音色的遮罩決定。

## 4. YM2203 合成（`internal/opn`）

純 Go 的 OPN 子集：三個 4-運算元 FM 聲道與三個 SSG 方波聲道。

**這一層是近似，不是週期精確的**：包絡用線性段近似對數包絡，
SSG 只做音調與音量（雜訊與硬體包絡沒做）。判準是
「旋律、節奏、速度與原版資料一致」，不是「波形與真機相同」。
真機比對要等到有音源 BIOS ROM 或真機錄音。

`internal/opn` 不認識 MSCDRV，只吃暫存器寫入與時間；
`internal/mscdrv` 的音序器負責把演奏資料翻成暫存器寫入。

## 5. 驗收——已經通過

1. **跑起來的驅動與靜態解析逐筆相同**：15 首 × 6 聲道 ＝ **90／90 個聲道**
   的區塊序列與長度完全一致。兩邊來源完全獨立——一邊在模擬的 CPU 上跑
   原版的 8086 碼，一邊照格式重寫（`golden-box-remake-engine` 的
   `audio/pc98mscdrv`）。對法見 `tools/compare-blocks.py`。
2. 15 首每一首都抽得到區塊，也都合成得出非靜音的音訊
   （`TestEveryTrackRendersAudibly`）。
3. 原版驅動不進版控；缺檔就 skip。

## 6. 對拍過程中抓到的坑

都是「看起來對、其實錯」的形狀，記在這裡不要再踩：

- **曲號是 0 起算的。** 減一那一步在 `GAME.EXE` 的播曲包裝裡，不在驅動裡。
  傳 1 起算時最後一首會落到曲目表外，把曲子資料當成指標讀——症狀不是
  報錯，是**驅動在自己的展開器裡空轉**。
- **驅動記的區塊位址是資料起點，不是區塊標頭**（標頭第一個位元組是長度）。
  差一個位元組，兩邊的座標系就對不起來。
- **安裝路徑已經替每個聲道抽掉第一個區塊**（`$008D` 對六個聲道各叫一次
  補資料常式）。不先把它讀出來，抽出來的序列會整體少掉開頭那一塊——
  而後面每一塊都還是對的，看起來只是「短了一點」。
- **結束與迴圈要分開判。** 串流走到結尾時驅動只把串流指標歸零、不動區塊表；
  但迴圈裡同一個區塊會被一交再交，區塊表也不動。只看其中一個都會錯：
  只看區塊表會在迴圈第一圈就停，只看長度會把最後一塊收兩次。
